## 1. 規約・ポリシー調査結果

### CORS と API Gateway HTTP API

| 項目 | 調査結果 | 出典URL |
|------|---------|---------|
| API Gateway HTTP API の CORS サポート | ✅ HTTP API は CORS をネイティブサポート。`corsPreflight` 設定で OPTIONS レスポンスを自動生成 | https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html |
| REST API vs HTTP API の CORS 差異 | ⚠️ REST API は Lambda で CORS ヘッダーを手動設定する必要あり。HTTP API は CDK の `corsPreflight` 設定のみでOK | https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-develop-integrations-lambda.html |
| `Access-Control-Allow-Origin: *` のリスク | ⚠️ `*` はクレデンシャル（Cookie / Authorization）を含むリクエストには使用不可。`x-api-key` ヘッダーを使う場合は特定オリジンの指定が必要 | https://developer.mozilla.org/ja/docs/Web/HTTP/CORS |
| Preflight リクエストへの課金 | ✅ API Gateway HTTP API の OPTIONS レスポンスは Lambda を呼び出さず API Gateway レベルで処理。Lambda 実行コストは発生しない | https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html |

**調査まとめ**: API Gateway HTTP API を使用する現設計は CORS 対応として最適な選択。`x-api-key` を Authorization ヘッダーとして渡す設計の場合、`Access-Control-Allow-Credentials: true` と特定オリジン指定の組み合わせが必要になる点に注意。

### CloudFront と S3 SPA ホスティング

| 項目 | 調査結果 | 出典URL |
|------|---------|---------|
| CloudFront での SPA ホスティング | ✅ `index.html` へのフォールバック設定が必要。`CustomErrorResponse` で 403/404 → 200/index.html にリダイレクト | https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/custom-error-pages.html |
| S3 バケットポリシー（OAC） | ✅ Origin Access Control（OAC）推奨。OAI（旧方式）は非推奨。CDK v2 では `S3Origin` がデフォルトで OAC を使用 | https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html |
| CloudFront Invalidation の制限 | ⚠️ 無料枠: 月1,000パス/月。超過後: $0.005/パス。`/*` 指定は1パスとしてカウント。デプロイ頻度が高い場合でも月1,000回以内なら無料 | https://aws.amazon.com/cloudfront/pricing/ |
| CDK での CloudFront + S3 構成 | ✅ `aws-cdk-lib/aws-cloudfront-origins` の `S3BucketOrigin.withOriginAccessControl()` が推奨 | https://docs.aws.amazon.com/cdk/api/v2/docs/aws-cdk-lib.aws_cloudfront_origins.S3BucketOrigin.html |

**調査まとめ**: CloudFront + S3 SPA ホスティングは AWS の標準構成として十分なドキュメントと CDK サポートがある。OAC（Origin Access Control）を使用した S3 バケットポリシーの設定が現在の推奨方式。

### Lambda Container Image と Web版のセキュリティ

| 項目 | 調査結果 | 出典URL |
|------|---------|---------|
| Lambda の x-api-key 認証 | ✅ API Gateway HTTP API でも x-api-key による認証は可能。ただし HTTP API ではリクエストごとの使用量プラン（Usage Plan）が設定できないため、単純な認証のみ | https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-key-auth.html |
| ブラウザからの API キー送信リスク | ⚠️ ブラウザ JavaScript から x-api-key ヘッダーを送信すると、DevTools で API キーが見える。React SPA から直接呼び出す場合のキー管理に注意が必要（CloudFront + Lambda@Edge での置換が理想） | https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-api-key-source.html |
| Lambda 関数 URL の代替 | ✅ API Gateway 不要で Lambda に直接 CORS 対応 URL を付与できる。コストが低いが WAF 適用不可、カスタムドメイン非対応 | https://docs.aws.amazon.com/lambda/latest/dg/lambda-urls.html |

**調査まとめ**: ブラウザから x-api-key を直接送信する設計はセキュリティリスクがある。CloudFront Functions で API キーをヘッダーに付与する方式（キーをフロントエンドに持たせない）か、Cognito 認証 + IAM 認可への移行を中長期で検討すること。

## 2. 追加ヒアリング事項

### 🔴 優先度：高（フェーズ0開始前に必須）

- **ブラウザからの API キー管理方針**
  - 質問: React SPA から VOICEVOX API を呼び出す際の認証方式を決めてください。①API キーをフロントエンドに持たせる（簡単だが漏洩リスク）②CloudFront Functions で API キーをヘッダーに付与する（推奨）③FastAPI バックエンド経由で呼び出す（最も安全だが二重 Lambda 呼び出しになる）
  - なぜ重要: フロントエンドの実装方式と CloudFront の設定に直接影響します。

- **iOS版と Web版での API キー共用可否**
  - 質問: iOS版と Web版で同一の API Gateway エンドポイント・API キーを共用しますか？
  - なぜ重要: 共用する場合、一方のキー漏洩が両版に影響します。環境を分けるかどうかを決定する必要があります。

- **ずんだもん商用利用規約の確認**
  - 質問: Web版でも VOICEVOX ずんだもん音声をサービスに組み込む場合の商用利用規約は確認・同意済みですか？
  - なぜ重要: iOS版・Web版ともに同じ確認が必要です。

### 🟡 優先度：中（フェーズ1開始前に確認）

- **CloudFront カスタムドメインの用意**
  - 質問: Web版のドメイン名（例: `englishlearn.example.com`）は決まっていますか？Route 53 と ACM 証明書の準備が必要です
  - なぜ重要: CORS の許可オリジン設定に本番ドメインが必要なため、フェーズ1 開始前に確定が必要です。

- **Lambda コールドスタート（10〜30秒）のブラウザ UX 許容範囲**
  - 質問: ブラウザユーザーに対して、初回音声生成に最大 30 秒かかる可能性があります。許容できますか？（許容できない場合は Provisioned Concurrency +¥52,000/月 が必要です）
  - なぜ重要: モバイルアプリと異なり、ブラウザユーザーはロード時間に敏感なためコールドスタートがユーザー離脱につながりやすいです。

- **iOS版 Lambda と Web版 Lambda の共用・分離**
  - 質問: VOICEVOX Lambda を iOS版と Web版で共用しますか？それとも環境を分けますか？
  - なぜ重要: 共用の場合は CORS 設定追加のみで済みます（+0.5人日）。分離する場合は別スタックでの管理が必要です（+5人日）。

### 🟢 優先度：低（フェーズ2以降でも可）

- **CloudFront WAF の適用**
  - 質問: ブラウザからのアクセスに対して WAF（DDoS・レートリミット）を適用しますか？（AWS WAF 料金: 約¥5,300/月〜）
  - なぜ重要: iOS版は固定台数のデバイスからのアクセスで悪用リスクが低いですが、Web版は不特定多数のブラウザからのアクセスがあるため WAF の適用を検討する価値があります。

- **CDK Pipelines への移行**
  - 質問: 現在 GitHub Actions での `cdk deploy` を予定していますが、将来的に CDK Pipelines への移行を検討しますか？
  - なぜ重要: マルチスタックが増えてきた場合、CDK Pipelines でデプロイ順序を自動管理できます。

## 3. 調査サマリーと推奨アクション

Web版 TTS インフラ固有の最大リスクは**ブラウザからの API キー露出**です。React SPA から x-api-key を直接送信すると DevTools で確認できてしまうため、CloudFront Functions でのキー付与または FastAPI バックエンド経由での呼び出しを推奨します。CORS 設定自体は API Gateway HTTP API の `corsPreflight` 設定で対応可能で技術的リスクは低いです。Lambda コールドスタート（10〜30秒）はブラウザユーザーへの影響が iOS版より大きいため、ローディング UI の実装と IndexedDB による積極的なキャッシュ活用が重要です。
