# 工数見積もりガイド（React / Python / AWS スタック）

このガイドは React + TypeScript（フロントエンド）、Python（バックエンド）、AWS（インフラ）を使った
Webアプリ・インフラ構築案件の工数見積もりの参考値です。

**単位**: 人日（1人日 = 8時間）
**前提**: 中級エンジニア1名が担当する場合の目安

## 6. テスト工数（詳細参考値）

**基本的な考え方**: テスト工数は「実装工数の 25〜35%」を目安とする。
ただし機能の種類・外部連携の有無・品質要件によって下記を参照して個別に積み上げること。

### 6-1. 単体テスト（Unit Test）

| テスト対象 | 工数（人日） | 備考 |
|-----------|------------|------|
| バックエンド API 1エンドポイント | 0.5〜1.0 | pytest / 正常系＋主要異常系3〜5ケース |
| LLM 分類ロジック / ビジネスルール | 1〜2 | モックを使った境界値テスト |
| 外部サービス連携（1サービス） | 1〜2 | モック（unittest.mock / pytest-mock）で HTTP 依存を分離 |
| バッチ処理・非同期ハンドラ | 1〜2 | SQS/Lambda イベントのモックテスト |
| フロントエンド コンポーネント | 0.5〜1.0/画面 | React Testing Library |
| DB リポジトリ層 | 0.5〜1.0 | pytest + testcontainers または SQLite インメモリ |

### 6-2. 結合テスト（Integration Test）

| テスト対象 | 工数（人日） | 備考 |
|-----------|------------|------|
| API エンドポイント（DB 込み） | 0.5〜1.0/エンドポイント | pytest + テスト用 DB（Docker Compose） |
| 外部サービス実連携（1サービス） | 1〜3 | サンドボックス/テスト環境が必要。環境準備含む |
| SQS → Lambda → DB の非同期フロー | 1〜2/フロー | LocalStack または実 AWS テスト環境 |
| 認証フロー（Cognito / JWT 等） | 1〜2 | テストユーザー作成・トークン発行フロー |
| メール送信（SES テストモード） | 0.5〜1.0 | SES sandbox でのテスト |

### 6-3. E2E テスト / システムテスト

| テスト対象 | 工数（人日） | 備考 |
|-----------|------------|------|
| 主要ハッピーパス 1フロー | 1〜2 | Playwright（UI） or pytest（API E2E）|
| 異常系・エラーリカバリーフロー | 0.5〜1.0/フロー | |
| 負荷・パフォーマンステスト（簡易） | 1〜2 | k6 / Locust で目標スループット確認 |
| セキュリティテスト（OWASP 基本） | 1〜3 | OWASP ZAP または手動検証 |

### 6-4. テスト環境構築

| 作業 | 工数（人日） | 備考 |
|------|------------|------|
| CI パイプラインへのテスト組み込み | 1〜2 | GitHub Actions + pytest / Jest |
| Docker Compose でのローカルテスト環境 | 0.5〜1.0 | DB・Redis・LocalStack |
| テスト用シードデータ作成 | 0.5〜1.0 | fixtures / factory_boy |
| ステージング環境（dev/stg 分離） | → 「4. AWS インフラ構築」の「マルチ環境構築」を参照 | |

### 6-5. テスト工数の見積もりパターン例

| システム規模 | 実装工数（目安） | テスト工数（目安） | 合計 |
|------------|---------------|----------------|------|
| 小規模 MVP（管理画面系） | 20〜30人日 | 6〜9人日 | 26〜39人日 |
| 中規模 Web アプリ | 50〜80人日 | 15〜25人日 | 65〜105人日 |
| Playwright 等の外部自動化を含む | 30〜50人日 | 12〜20人日 | 42〜70人日 |

> **外部サービス連携が多い・Playwright 等の脆弱な自動化を含む場合はテスト工数を多めに取ること。**
> E2E テストは実環境依存が高く、環境問題でテスト工数が膨らみやすい。

## 7. 見積もりパターン例

### 小規模WebアプリMVP（管理画面系）
- 認証 + 2〜3画面 + CRUD API + RDS + 基本インフラ
- **目安: 20〜35人日**

### 中規模Webアプリ
- 認証 + 5〜10画面 + API多数 + 外部連携1〜2件 + CI/CD
- **目安: 50〜100人日**

### インフラ構築のみ
- マルチ環境 + CI/CD + 監視
- **目安: 15〜25人日**

## 8. バッファの考え方

| リスクレベル | バッファ率 | 状況 |
|------------|----------|------|
| 低 | +15〜20% | 要件明確・技術既知・類似案件あり |
| 中 | +25〜30% | 要件に不明点あり・新技術あり |
| 高 | +35〜50% | 要件不明確・未経験技術・大規模連携 |

---

## 9. 注意事項

- 上記はあくまで参考値。要件の複雑度・品質要求・チーム習熟度によって大きく変わる
- 「要件が不明確」な箇所は工数の見積もり幅を広く取ること
- フェーズ1（MVP）とフェーズ2（拡張）に分けることで、初期見積もりの精度を上げられる
- 初回見積もりは「概算」と明示し、詳細ヒアリング後に確定見積もりを出す
